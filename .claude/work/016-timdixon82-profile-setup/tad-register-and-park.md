## What this repository does

`timdixon82/timdixon82` is a GitHub special repository. When its name matches the account login, GitHub treats it differently from every other repository. If a file named `README.md` exists on the default branch, GitHub renders it as the first thing a visitor sees when they open `https://github.com/timdixon82`. Without a `README.md`, visitors see the default GitHub profile view: a list of Tim's public repositories, sorted by activity. There is no personal introduction and no description of his work or interests.

Adding a `README.md` to the default branch changes that immediately. The text becomes the first impression for anyone who finds Tim on GitHub, including recruiters, collaborators, and people who have read his blog and want to know more.

## Recommendations for content

A profile README typically does five things. Each one should match the same screen-reader-friendly standards the team uses everywhere else.

1. Introduces Tim by name and says what he does in one or two sentences.
2. Names his current projects with descriptive link text, not bare URLs.
3. States his accessibility focus, using plain language.
4. Links to his contact page at [Tim Dixon contact form](https://www.timdixon.net/contact/).
5. Keeps the tone warm and plain-spoken, in keeping with Tim's voice as described in `docs/writing-style.md`.

Structure rules that apply to the README itself:

- One H1, which is Tim's name or a short greeting. No skipped heading levels below it.
- Short paragraphs, two to four sentences each.
- No decorative emoji-led headings and no ASCII art dividers.
- Plain language at roughly Flesch-Kincaid grade 9 or below.
- Descriptive link text throughout.

These rules follow the "Things to avoid" and "Structure and rhythm" sections of `docs/writing-style.md`.

## Three example structures

These are structural outlines only. None of this is the actual README. Tim decides when and what.

### Structure A: Introduction first

1. H1: Tim's name.
2. Short paragraph: who Tim is and what he works on.
3. H2: Current projects. A short bulleted list with descriptive link text for each project.
4. H2: Accessibility. Two or three sentences on why accessibility matters to Tim, in first person.
5. H2: Get in touch. A single sentence linking to the contact page.

This structure suits someone landing on the profile cold with no prior knowledge of Tim.

### Structure B: Projects first

1. H1: Tim's name.
2. H2: What I am working on. A short bulleted list of current projects with descriptive link text.
3. H2: About me. Two or three sentences on Tim's background, accessibility focus, and lived experience.
4. A short closing sentence linking to the contact page.

This structure leads with Tim's output, which suits visitors coming from a technical context who want to see work before biography.

### Structure C: Accessibility focus first

1. H1: Tim's name.
2. One-sentence hook about accessibility or inclusion, in Tim's voice, for example a plain statement of what he cares about.
3. H2: What I do. A short paragraph covering Tim's professional and personal context.
4. H2: Projects. A bulleted list with descriptive link text.
5. A closing sentence linking to the contact page.

This structure leads with values, which suits visitors who already know Tim from his blog or community work.
